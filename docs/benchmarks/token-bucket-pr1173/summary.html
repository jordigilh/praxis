Recommendation: keep the mutex compound-state implementation. It fixes the race by updating the token count and refill timestamp as one logical transition, preserves the existing API, and is fastest in the simple and low- contention paths. High-contention throughput should be addressed with a correctness-preserving design such as sharding or striped buckets.

Implementations

Mutex compound state

The production implementation stores { tokens: f64, last_refill: u64 } behind parking_lot::Mutex. Refill, admission, decrement, and timestamp update happen under one lock.

Pros:

  • Preserves exact fractional-token and introspection behavior.
  • Simple linearizable transition with blocking waiters.
  • Fastest measured option in the simple and low-contention paths.

Cons: serializes a hot bucket under high contention.

Split atomics

The historical implementation stores tokens and the timestamp in separate atomics. Its token CAS does not include the timestamp, so the compound state is not updated atomically.

Pros: low-cost 64-bit atomics and excellent apparent contention throughput.

Cons: the token/timestamp transition is not atomic, so the implementation can over-admit requests. Performance baseline only.

Locked split fields

Two atomic fields protected by an atomic spin lock. This restores correctness without requiring a 128-bit atomic, but it serializes the same logical update.

Pros: preserves the current state representation and is correct without double-width atomics.

Cons: spinning burns CPU, can starve, and loses the apparent split-atomic advantage under contention.

Virtual time / GCRA

A single atomic theoretical-arrival timestamp represents admission debt and burst tolerance. It avoids the split-state race, but changes how bucket state is represented and observed.

Pros: one atomic schedule value, cheap rejection, and strong high-contention results.

Cons: changes fractional-token and introspection semantics; algorithmic alternative, not integrated into production.

Why Split Atomics Are Unsafe

The token CAS does not include last_refill. For example, with one token, a burst of at least two, and one token refilled by 100 ms, two threads can both read the same state, calculate tokens = 2, and successfully CAS 1 -> 1. A third request at the same timestamp can then also succeed. The mutex prevents this by making the refill and decrement one operation.

Correctness-Restored Split Retry

The retry added an atomic spin lock around the two split fields. It passed the remote benchmark checks and three independent contention rounds, but it did not retain the historical split-atomic advantage. At 16 workers, successful acquisition was 855.690 ns versus 817.370 ns for the mutex; rejected acquisition was 1,039.6 ns versus 798.490 ns. The result is correct, but the synchronization cost is now visible.

This is a valid correctness-preserving option, not a lock-free option. A packed 128-bit CAS would be a separate design with different portability and retry costs.

Virtual Time Tradeoffs

Advantages

  • One atomic state value and no split token/timestamp race.
  • Very cheap rejection path because rejected requests do not write state.
  • Better successful-path contention results than the mutex in this benchmark at 8 and 16 workers.
  • Common algorithmic family used by governor and Envoy.

Costs

  • Replaces explicit fractional tokens with an implicit scheduling debt.
  • Does not directly preserve current_tokens() or last_refill_nanos().
  • Requires validation for rate conversion, burst rounding, timestamp boundaries, and clock rollback.
  • Not a drop-in production implementation; only the benchmark candidate has been tested.

What About 128-bit CAS?

Packing the existing f64 token bits and u64 timestamp into one 128-bit CAS word could preserve current semantics. However, native 128-bit atomic support is architecture- and CPU-dependent. A portable fallback may use locks, and under contention CAS retries can be worse than parking on a mutex. It would require a separate prototype, target support policy, stress tests, and benchmark validation before replacing the mutex.
